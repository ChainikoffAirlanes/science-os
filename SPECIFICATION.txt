1. ТЕХНОЛОГИЧЕСКАЯ АРХИТЕКТУРА

Используй максимально простой, стабильный, бесплатный и поддерживаемый стек.

1.1 Frontend

* React.
* TypeScript со строгой типизацией.
* Vite.
* Tailwind CSS.
* shadcn/ui.
* Lucide React.
* TanStack Query.
* React Hook Form.
* Zod.
* Recharts.
* TanStack Table.
* Подходящая поддерживаемая библиотека для CSV/XLSX.
* Подходящая библиотека для создания PDF с поддержкой русского текста.
* Playwright для E2E-тестирования.
* Vitest для модульных тестов.

Используй стабильные совместимые версии библиотек, существующие в момент разработки.

Не добавляй сложные зависимости без необходимости.

1.2 Backend

Используй Supabase:

* PostgreSQL для основной базы данных.
* Supabase Auth для регистрации и входа.
* Supabase Storage для файлов.
* Supabase Realtime для совместной работы.
* PostgreSQL RLS для контроля доступа.
* PostgreSQL-функции RPC для операций, требующих атомарности или повышенных прав.

Отдельный Node.js backend не требуется.

Не использовать собственный сервер, постоянно работающий компьютер пользователя, VPS или Docker для публичной эксплуатации.

1.3 Hosting

Используй:

* GitHub для исходного кода.
* GitHub Pages для публикации сайта.
* GitHub Actions для автоматической сборки и развёртывания.

Предполагаемая структура адреса:

https://USERNAME.github.io/science-os/

USERNAME должен определяться из реально авторизованного GitHub-аккаунта, а не быть вымышленным.

GitHub Pages публикует только frontend. Пользовательские данные, файлы и авторизация размещаются в Supabase.

1.4 Маршрутизация

Для максимальной совместимости с GitHub Pages выбери HashRouter.

Основные пути:

* /#/login
* /#/register
* /#/forgot-password
* /#/dashboard
* /#/projects
* /#/projects/new
* /#/projects/:id
* /#/projects/:id/experiments
* /#/projects/:id/experiments/:experimentId
* /#/projects/:id/analytics
* /#/projects/:id/files
* /#/projects/:id/team
* /#/projects/:id/tasks
* /#/projects/:id/report
* /#/publications
* /#/publications/:id
* /#/opportunities
* /#/opportunities/:id
* /#/notifications
* /#/profile
* /#/settings
* /#/invite/:token

Реализуй корректную обработку подтверждения email и восстановления пароля с учётом того, что Supabase может возвращать код авторизации в URL.

Используй PKCE, если он совместим с выбранной схемой авторизации.

Обрабатывай auth callback до монтирования маршрутизатора при необходимости.

Не допускай конфликта URL-фрагмента HashRouter с параметрами авторизации.

Настрой правильный Vite base path для GitHub Pages.

* Создание строк.

* Создание столбцов.

* Изменение единиц измерения.

* Проверка значений.
* Навигация с клавиатуры.

9.5 Сохранение

Изменения должны записываться в Supabase.

Предпочтительно сохранять на уровне отдельных ячеек, а не всей таблицы.

При быстром вводе допустим короткий debounce, но нельзя терять изменения при переключении страницы или закрытии редактора.

Перед уходом со страницы проверять наличие незавершённых изменений.

При ошибке сохранения показывать Retry.

11.5 Защита от конфликтов

Не использовать безусловное перезаписывание целой таблицы последним отправившим пользователем.

Для редактируемых записей использовать контроль версии.

Каждая ячейка или минимальная редактируемая сущность должна иметь version.

При сохранении:

1. Клиент отправляет ожидаемую версию.
2. База выполняет условное изменение.
3. Версия увеличивается.
4. Изменение передаётся остальным пользователям.

Если версия устарела:

* Не перезаписывать чужие данные молча.
* Показать пользователю новое значение.
* Предложить повторное применение собственного изменения.
* Дать возможность отмены.

Обрабатывать и одновременное создание одной ранее пустой ячейки.

Использовать атомарную RPC-функцию либо другую корректную транзакционную реализацию.

11.6 Presence

В правой части панели редактора отображать аватары активных участников.

При наведении:

* Имя.
* Статус online.

Необязательно реализовывать курсоры с посимвольной точностью.

Достаточно настоящего присутствия и синхронизации изменений.

Права на Realtime-каналы должны соответствовать доступу к проектам.

20. DATABASE SECURITY

Безопасность обязательна даже для школьного проекта.

20.1 RLS

Включить Row Level Security на всех таблицах с пользовательскими данными.

Основная логика:

* Owner имеет доступ к собственному проекту.
* Editor имеет разрешённый доступ к совместному проекту.
* Viewer имеет только чтение.
* Посторонний пользователь не получает доступа.
* Учитель не получает автоматически доступ ко всем частным проектам.
* Публикация не открывает исходные приватные таблицы.

20.2 RPC

Для чувствительных операций использовать PostgreSQL RPC:

* Создание приглашения.
* Принятие приглашения.
* Отзыв приглашения.
* Атомарное редактирование ячейки.
* Изменение роли участника, если требуется.
* Назначение владельца при создании проекта.

RPC-функции обязаны проверять auth.uid().

Если используется SECURITY DEFINER:

* Явно задавать безопасный search_path.
* Ограничивать EXECUTE.
* Проверять права внутри функции.
* Не доверять переданному user_id.
* Не создавать обход RLS для посторонних пользователей.

20.3 Secrets

Нельзя публиковать:

* Supabase service_role key.
* Supabase secret keys.
* GitHub access tokens.
* Passwords.
* Database passwords.

Разрешённые клиентские Supabase URL и publishable/anon key можно использовать во frontend только при корректной конфигурации RLS.

Не считать клиентский ключ полноценной защитой.

20.4 Files

Все приватные файлы должны находиться в приватном bucket.

Проверки прав должны выполняться серверной стороной Supabase, а не только скрытием кнопок.

20.5 Пользовательский контент

Защитить интерфейс от XSS.

Не рендерить пользовательский HTML без надёжной очистки.

Ограничить размеры текстовых полей и загрузок.

Не раскрывать приватные данные в логах, сообщениях об ошибках и аналитике.

22. ПОВЕДЕНИЕ ИНТЕРФЕЙСА

Для каждой интерактивной функции соблюдать следующие правила.

22.1 Кнопки

Каждая кнопка:

* Выполняет настоящее действие.
* Имеет hover state.
* Имеет focus state.
* Имеет disabled state при необходимости.
* Показывает loading state при сетевой операции.

Кнопка не должна визуально выглядеть рабочей, если не имеет обработчика.

22.2 Формы

Все формы:

* Проверяют обязательные поля.
* Показывают конкретные ошибки.
* Не отправляют некорректные значения.
* Не создают дубликаты при двойном нажатии.
* Корректно обрабатывают ошибки сети.
* Сохраняют данные только после успешной серверной операции.

22.3 Уведомления

Использовать Toast-компоненты.

Успех:

Проект успешно сохранён.

Ошибка:

Не удалось сохранить изменения. Повторите попытку.

Не показывать пользователю сырые SQL-ошибки.

22.4 Подтверждения

Опасные операции требуют подтверждения:

* Удаление проекта.
* Удаление эксперимента.
* Удаление файлов.
* Исключение участника.
* Публикация приватного исследования.

22.5 Loading

Использовать skeleton loading.

Не показывать пустую таблицу как окончательное состояние, если данные ещё загружаются.

22.6 Ошибки

Добавить:

* 404 Not Found.
* Access Denied.
* Network Error.
* Session Expired.
* Empty State.
* Unexpected Error.

Использовать Error Boundary.

* Отписка от каналов при закрытии страницы.
* Отмена устаревших запросов.
* Debounce поиска.
* Оптимизация графиков с большими наборами данных.
* Проверка bundle size.

Не допускать бесконечных повторных запросов.

Не допускать утечек подписок Realtime.
